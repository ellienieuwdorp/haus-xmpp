# OMEMOCrypto

An isolated, synchronous Apple-platform package for OMEMO cryptographic operations. It has no UI, XMPP networking, database, logging, account service, or paid dependency. The business coordinator belongs in `Packages/OMEMO`; keeping the cryptographic engine separately testable lets wire interoperability and durable transaction behavior evolve independently.

## Dependency decision

The Double Ratchet, X3DH, Curve25519/Ed25519 conversion, signatures and Signal/OMEMO protobufs come from **unmodified libomemo-c 0.5.1**, upstream revision `1f0b37fee3ebefc46c32f882623481899a1ba568`. This is Dino's maintained upstream library, not an application fork we maintain. The exact source is vendored because upstream does not ship a Swift package. `VendorManifest.json` pins every upstream file; `Scripts/verify_vendor.py` verifies hashes. Updates replace the upstream inventory and rerun interoperability tests; do not patch cryptographic source locally.

The thin original bridge supplies Apple's CommonCrypto SHA/HMAC/AES and Security random generator callbacks plus an in-memory record store. Swift uses CryptoKit for AES-GCM, HKDF and HMAC. No cryptographic primitive or ratchet has been reimplemented here. `protobuf-c` 1.5.2 (revision `4719fdd7760624388c2c5b9d6759eb6a47490626`) supplies the generated protobuf runtime.

## Profiles and boundary

- `.legacy`: `eu.siacs.conversations.axolotl`, Signal protocol 3; 33-byte serialized public keys, AES-128-GCM payload, 12-byte IV, 16-byte key + 16-byte authentication tag inside the ratchet.
- `.modern`: `urn:xmpp:omemo:2`, libomemo-c protocol 4; 32-byte Ed25519 identity, 32-byte Montgomery prekeys, AES-256-CBC + HMAC-SHA256/128 payload with HKDF-SHA256 `OMEMO Payload`; 32-byte random key + 16-byte tag inside the ratchet. The IV is derived, never a modern envelope field. The coordinator must construct and authenticate SCE.

`OMEMOEngine.fingerprintBytes(for:profile:)` returns the raw 32-byte Curve25519 fingerprint recommended by XEP-0384, converting modern Ed25519 wire keys through upstream code. Use these bytes for user-visible fingerprints, while pinning and comparing the complete original identity key in trust state.

Legacy receive also accepts the older 16-byte ratcheted key with the GCM tag appended to payload. Key length selects the representation; authentication failure never triggers an alternate-format retry. This deployed compatibility behavior is corroborated by [Monal MLOMEMO.m, revision a206db3](https://github.com/monal-im/Monal/blob/a206db31f552dd0884a6cdf7af096a5a89fec586/Monal/Classes/MLOMEMO.m#L1487).

`AttachmentCrypto.seal/open` implements [XEP-0454](https://xmpp.org/extensions/xep-0454.html) key plumbing with CryptoKit AES-256-GCM: ciphertext followed by a 16-byte tag, separate random 32-byte key and 12-byte IV. The default in-memory bound is 32 MiB. No upload, URL navigation, thumbnail decoding, or media UI is included; the key/IV must remain inside encrypted message content. Large-file streaming is a future media-pipeline concern.

When advertising the same physical device ID in both profiles, initialize the second profile with `OMEMOEngine(profile: .modern, sharingIdentityWith: legacy)`. Both profiles must represent the same identity keypair; their signed prekeys, one-time prekeys, sessions and snapshots remain separate. Independent per-profile identity generation under one numerical device ID fails unified-client interoperability. Never replace an existing published identity silently.

`OMEMOEngine` is deliberately not `Sendable`. One ephemeral instance represents exactly one account, device and profile. Load it from a snapshot within the coordinator's transaction scope, explicitly pin an accepted remote identity with `trustIdentity`, establish sessions as required, encrypt/decrypt, then atomically persist `snapshot()` together with the resulting message and immutable ciphertext. A failed operation or database transaction requires discarding the instance. Never send ciphertext before its advanced state and outbox record are durable; never regenerate ciphertext to retry a possibly sent stanza.

Unknown identities are rejected. Changed identities are rejected until the caller explicitly accepts the fingerprint and uses `trustIdentity(..., resetSession: true)`, which drops the stale peer session. The engine does not decide UI trust, canonicalize JIDs or associate stanza authors; those are coordinator responsibilities. Trust and session keys are indexed by complete peer bare JID + device ID and never shared across profile/account snapshots.

Snapshots include the private identity, signed prekey, remaining one-time private prekeys, remote identity pins, sessions/skipped message keys and monotonic next-prekey ID. **Snapshots are secret plaintext data.** The caller must protect them at rest, exclude them from backups/logs, and serialize all mutation via durable compare-and-swap/transactions. Swift `Data` makes copies, so complete secret zeroization cannot be claimed; the C record and temporary-buffer cleanup uses wiping before free. `replenishPreKeys` fills consumed slots using new IDs. `rotateSignedPreKeyIfNeeded` rotates weekly and retains retired signed private prekeys for 30 days after retirement, then wipes them. Call it during initialization/maintenance and persist before publishing the refreshed bundle. Rotation timestamps and active IDs survive snapshots. Consumed one-time private prekeys are deleted immediately: XEP-0384 §8 explicitly permits this to avoid unsafe sending on duplicate-PreKey sessions. Repeated key-exchange wrappers for an established session remain processable; a genuinely different, delayed initiation reusing a consumed prekey must fail and require user-mediated recovery. This chooses the allowed security tradeoff over retaining consumed prekeys without duplicate-session send blocking.

## Validation and limits

Run `swift test --package-path Packages/OMEMOCrypto` and `python3 Packages/OMEMOCrypto/Scripts/verify_vendor.py` from the repository root. AddressSanitizer is supported with `swift test --package-path Packages/OMEMOCrypto --sanitize=address`.

Tests cover both profiles: session setup; encrypted reply; restart from persisted snapshots; out-of-order receive; duplicate rejection; consumed prekey replenishment; invalid bundle signature; unknown/changed identity rejection; sender-address separation; corrupted ciphertext/payload authentication; profile mismatch and malformed snapshot/device input; weekly signed-prekey rotation, decrypting a delayed message from a retired bundle after restart, and eventual old-key deletion. Independent interop additionally exchanges persisted ratchet messages in both initiation directions against Python oldmemo/twomemo 2.1.0, using a harness that is not part of this repository. This is stronger than a same-implementation round trip, but is not a security audit or a claim of production readiness. Real-device lifecycle/notification testing remains required.
